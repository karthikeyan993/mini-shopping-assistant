1AI Fundamentals (Visual Mental Models)

Every chatbot design decision flows from three simple truths about LLMs: (1) an LLM is a stateless next-token predictor, (2) embeddings turn meaning into geometry, and (3) structured outputs + code validation bridge probabilistic AI to deterministic databases.

1.2 Embeddings: Turning meaning into geometry

An embedding model maps a sentence into a fixed-length vector of numbers — here 768 floats from gemini-embedding-001 (truncated from 3,072 via Matryoshka representation = 4× smaller memory & faster math). Similar meanings land close together in angle, even across Thai and English.

1.3 Bridging AI to Code: Structured Outputs + Pydantic Validation

Predict before peeking: Why does agent.py send the assistant's tool-call message back unchanged (msg.model_dump(exclude_none=True)) instead of rebuilding a dict with just role and tool_calls?
On Gemini's OpenAI-compatible endpoint, tool-call responses carry an internal thought signature. Stripping it causes Gemini to reject or degrade the follow-up turn. Forwarding the assistant message object intact preserves that signature. Mentioning real provider quirks like this in an interview proves you actually built and debugged with Gemini!

2Hybrid Search, Thai NLP & Scaling to 2M Rows

Retail search is never "just vector search". A shopper asking for "blue running shoes in stock under 3,000 baht for flat feet" mixes hard constraints (category, color, price, in_stock) with soft intent ("for flat feet") and sometimes exact model codes (Pegasus 41, Yonex). Pure vectors break on exact filters and SKU names; pure keywords break on synonyms and phrasing. Hybrid search lets each tool do what it is best at.

2.2 The Thai tokenization trap (src/shop/thai.py)

Thai has no spaces between words. Standard tokenizers (including SQLite FTS5's unicode61) see a whole Thai sentence as one giant word — so a shopper searching รองเท้าวิ่ง ไนกี้ สีดำ gets zero keyword matches unless you segment both index-time text and query-time text the exact same way.

Predict before peeking: Why does db.py store a precomputed products.in_stock flag AND still query the live stock table inside tools.check_stock()?
Fast filtering vs exact truth. During catalog search over 2M products, joining a huge store×size stock table (2M × 6 sizes × 20 stores = 240M rows!) on every search is too slow — a precomputed boolean in_stock column updated asynchronously by stock-change events makes filtering instant. Then, when a customer asks "is size 42 in stock at CentralWorld right now?", check_stock reads live quantities directly from stock without touching any cache.

5.2 The Adaptation & Fine-Tuning Ladder (Central Tech's "Minor Model Tuning")

Central Tech runs fine-tuned open models plus Gemini. If an interviewer says "Can we fine-tune a model on our website?", they are testing whether you know when NOT to fine-tune (fast-changing facts like stock, prices, promos → RAG / SQL tools!) versus when fine-tuning genuinely wins (consistent style, Thai retail jargon, strict JSON/tool formatting, distilling Gemini into a fast cheap open model via LoRA).

Trap · "Just fine-tune a model on our website!"

Never agree blindly! Explain: fine-tuning teaches behaviour (how to talk, Thai tone, strict JSON/tool habits), NOT volatile facts. If you bake today's prices and promotions into model weights, they go stale tomorrow and cause hallucinations you can't easily delete. Instead: crawl & index the website into Hybrid RAG + live SQL tools for facts, and use LoRA fine-tuning on logged/curated conversations only if you need consistent brand tone or cheaper/faster inference on a smaller open model (served via vLLM).

6The "What to Break" Lab (10 Experiments)

Passive code reading fades in 24 hours. Deliberately breaking one safeguard at a time burns the exact failure mode into your memory so you can describe it effortlessly in the interview. After each experiment, restore cleanly with git checkout -- src/.

LAB 01 Break Filter Extraction (Vectors Alone on Price/Stock)

What to breakIn search.py:149, temporarily set where, params = "1=1", [] so SQL filters are skipped.
Run & observeuv run shop search "blue running shoes in stock under 3000 baht" → watch sold-out, red, or ฿5,000+ shoes appear!
Interview takeawayEmbeddings capture semantics, never exact inequalities or booleans. Extract filters to SQL; embed only the fuzzy remainder.

LAB 02 Break Thai Word Segmentation

What to breakIn thai.py:41, return normalise(text) immediately without calling _segmenter(), then reload DB (shop load).
Run & observeuv run shop search "รองเท้าวิ่ง ไนกี้ สีดำ ใส่วิ่งไกล" → notice keyword#- disappears on hits!
Interview takeawayThai has no spaces; without dictionary-aware segmentation (with brand spellings like ไนกี้), BM25 loses exact brand recall.

LAB 03 Break RRF With Naive Raw Score Addition

What to breakPrint raw SQLite bm25() (negative, e.g. -12.4) vs cosine (0.68) inside search.py.
Run & observeNotice the wildly incompatible scales and signs; changing RRF_K = 60 to RRF_K = 1 makes #1 dominate too sharply.
Interview takeawayRRF (1/(60+rank)) needs no calibration weights and naturally promotes items confirmed by both keyword and vector search.

LAB 04 Break Model Collapse & Category Diversity

What to breakIn search.py:169–171, comment out collapse() and diversify().
Run & observeRun shop search "running shoes" and shop search "gift for my dad who hikes" → same shoe in 5 colours or 5 identical items fill the page!
Interview takeawayRetrieval accuracy ≠ shopper UX. Collapsing variants by model_id and capping items per category dramatically improves open queries.

LAB 05 Inspect Indexed vs Full-Scan SQL Plans

What to runCompare shop explain-sql '{"category":"running shoes","in_stock":true,"max_price":3000}' vs '{"size":"42"}'.
ObserveFirst prints SEARCH products USING INDEX idx_cat_stock_price; second prints SCAN products (full table scan!).
Interview takeawayAt 2M rows, LIKE '%,42,%' dies on a full scan. Move to PostgreSQL text[] + GIN index or normalized stock table!

LAB 06 Break the Clock & Period Resolver

What to breakInspect timeutil.py and imagine removing Now: {now} from agent.py:22 or letting the LLM pass raw dates for "last week".
Run & observeRun uv run shop ask "what's today's date?" "show my orders from last week" --user u1 and check the exact tool trace get_orders({"period": "last_week"}).
Interview takeawayLLMs guess dates from training cutoffs and bungle Monday–Sunday + UTC+7 boundaries. Always inject Bangkok time and compute intervals in code.

LAB 07 Test Cross-User Order Access (IDOR)

What to testAs --user u1, ask for one of u2's order IDs (check evals.py:28 or run shop eval --only agent-other-users-order).
Observetools.get_order binds ctx.user_id in SQL and replies identically to a missing order — zero confirmation that u2's order exists.
Interview takeawayNever trust the LLM with identity. Authorization lives in the backend session context, never in tool parameters.

LAB 08 Break PII Checksums

Interview takeawayNaive regex PII masking wrecks order/tracking numbers; checksum validation (mod-11 Thai ID, Luhn card) gives high precision at zero latency.

LAB 09 Trigger the Price Grounding Rewrite

9.1 Interactive 60-Second Interview Drill (Top 12 Central Tech Questions)

Filter by topic & test yourself out loud first

Speak your answer before clicking "Show 4-part answer". Aim for calm, concrete engineering — cite real files and numbers.

Agent & Time
1. "What's today's date?" & "Show my orders from last week"
What: Inject Bangkok time + Buddhist Era (+543) in the system prompt; for ranges, LLM passes a named enum (period="last_week") and code computes exact bounds.
Why: LLMs have no clock and fail date/timezone arithmetic. Converting Bangkok midnight to UTC ISO before SQL prevents late-evening order drift.
Alternative: Letting the LLM emit start_date/end_date directly — works sometimes, silently breaks on week boundaries & leap/month edges.
Breaks if: "Last week" means Mon–Sun vs trailing 7 days — always state the resolved dates in the reply so the shopper can correct you.
Search & DB
2. "Blue running shoes in stock under 3,000 baht" (2M rows & filters)
What: Extract structured filters with json_schema + Pydantic → exact SQL WHERE on B-tree indexes → hybrid BM25 + vector ranking on fuzzy text → RRF → collapse by model_id.
Why: Vectors can't enforce <= 3000 or in_stock. Embedding 1 vector per model (552 vs 2,327 SKUs) cuts index size 4×.
Alternative: Pure vector search with post-filtering — returns 0 hits when filters match <1% of 2M rows.
Breaks if: HNSW stops early on rare filters → use pgvector 0.8+ hnsw.iterative_scan = relaxed_order, composite index (category, in_stock, price), and GIN/join for sizes.
Thai NLP
3. Mixed Thai/English search ("ไนกี้ pegasus สีดำ")
What: NFC normalise + Thai digits → Arabic + PyThaiNLP newmm with a custom trie containing catalog brand/colour spellings, paired with multilingual Gemini embeddings.
Why: Thai has no spaces; stock dictionaries split brand transliterations like ไนกี้ → ไน + กี้. Gemini embeddings scored 0.86 TH↔EN vs OpenAI small's 0.36.
Alternative: Pure dense embeddings without BM25 — misses exact SKU/model codes like "Pegasus 41".
Breaks if: Index-time and query-time analyzers diverge, or new brand spellings aren't added to the custom dictionary.
Document RAG
4. Retrieving rules from docs where one keyword ("leave" / "return") appears everywhere
What: Structure-aware chunking by section heading + breadcrumb prefix (Returns > Footwear > Worn), metadata filtering (topic/site/item), hybrid retrieval, then a cross-encoder/LLM reranker.
Why: When a word appears in every chunk, BM25 IDF drops to near-zero and naive chunks separate rules from their exceptions. Rerankers score (query, chunk) jointly.
Alternative: Fixed 500-character chunks + cosine top-3 — routinely grabs the general 30-day rule and misses the "worn shoes" exception.
Breaks if: Contradictory old/new policy versions stay in the index → track effective dates/version metadata and cite exact policy IDs.
Guardrails
5. "How do you set guardrails that actually work?"
What: 4 code layers: (1) PII masking, (2) cheap regex + fast-LLM scope/injection screen, (3) read-only tool whitelist + Pydantic + session auth + step/loop caps, (4) output price grounding.
Why: System prompts are suggestions; code enforces invariants. The safest way to stop a bot from giving 90% discounts or cancelling orders is not having those tools.
Alternative: Relying on prompt rules or only a heavy LLM judge — slow, bypassable, and misses arithmetic/price hallucinations.
Breaks if: Over-aggressive scope blocks hurt revenue (false positives like blocking "what's today's date?") → measure both recall & false positives in shop eval.
Privacy / PII
6. Users paste phone numbers, Thai IDs & cards — and chat goes to Gemini
What: Mask PII into placeholders (<PHONE_1>, <THAI_ID_1>) before the message leaves our server or hits logs; unmask only when returning the final text to that user.
Why: Keeps raw customer PII out of external LLM providers and analytics logs (PDPA compliance in Thailand), while checksum validation (mod-11 Thai ID, Luhn card) prevents false masks on order IDs.
Alternative: Sending raw text to Vertex AI zero-data-retention only — better than consumer APIs, still leaves PII in internal logs/evals.
Breaks if: Free-text street addresses aren't caught by regex → add a lightweight NER/Presidio detector if address masking is required.
Security / Agent
7. Indirect prompt injection, runaway tool loops, or reading another user's orders
What: Inject ctx.user_id strictly from login session (never a tool arg), identical error for missing vs other-user order, cap MAX_STEPS=5, stop identical tool calls >2×, treat tool output as untrusted data.
Why: A poisoned product review or hostile prompt can hijack LLM arguments; server-side auth & hard loop limits bound blast radius and cost.
Alternative: Passing user_id in tool JSON or trusting unlimited ReAct loops — classic IDOR breach & runaway token bills.
Breaks if: You later add mutating tools (cancel/refund) → require explicit deterministic confirmation + out-of-band auth, never single-turn LLM execution.
Vision
8. Customer uploads a shirt photo: "Do you have this?"
What: Path 1: VLM reads photo into strict JSON attributes (is_product_photo, category, dominant colour, pattern, sleeve) → reuses hybrid search. Path 2 (with catalog images): multimodal CLIP/SigLIP image embeddings + SQL filters.
Why: Path 1 works immediately even without clean studio photos and respects live stock/price filters. Filtering on dominant colour only (colors[:1]) stops striped shirts matching plain white shirts.
Alternative: Pure image similarity without filters — returns sold-out or wrong-price lookalikes.
Breaks if: Blurry/dark/non-product uploads or subtle prints → gate on is_product_photo, ask a clarifying follow-up, and combine Path 1 + Path 2 at scale.
PDF Tables
9. Reading a size chart / spec table in a PDF
What: Render PDF pages to PNG (pypdfium2) + attach text layer → vision model outputs typed JSON rows → deterministic sanity checks (50 ≤ min < max ≤ 180, monotonic) → code picks the size.
Why: pypdf text layers lose column alignment and regex breaks on the next supplier's layout; Gemini's OpenAI-compat endpoint 400s on raw PDF parts; LLMs misread boundary numbers.
Alternative: Dedicated layout OCR (Document AI / Docling) — great for massive batch ingestion; VLM + validation is super flexible for varied supplier charts.
Breaks if: Vision model misreads a digit (e.g. 108 → 18) or swaps inches/cm → unit conversion checks & human spot-audit on ingest.
Fine-Tuning & ML
10. "Fine-tune a model on our website" & intent classification
What: Climb the ladder: Prompting → Hybrid RAG/Tools (for facts!) → Embeddings + Logistic Regression classifier (0.97 F1 vs 0.70 TF-IDF, 0.45 confidence threshold) → LoRA/QLoRA fine-tuning on curated chats.
Why: Never fine-tune to memorize volatile prices/stock. Fine-tune (LoRA) for consistent brand tone, Thai retail slang, strict tool formatting, or distilling Gemini into a fast cheap open model on vLLM.
Alternative: Full fine-tuning or baking catalog facts into weights — expensive, stale within hours, and hard to unlearn.
Breaks if: Training on uncleaned synthetic/noisy chats causes catastrophic forgetting or wrong confidence thresholds → always evaluate against a human-labelled held-out set.
Routing & Latency
11. Answers take 8s, cost too much, or Gemini hits rate limits
What: Profile first (here filter extraction was 85% of search latency!), use small/fast models for routing & extraction, cache slow-changing searches in Redis (never live stock/orders), stream tokens, retry transient errors with jitter, and fail over via an OpenAI-compatible gateway (LiteLLM) to backup models/providers.
Why: Keeps p95 fast, cuts spend 5–10× by routing simple intents to fine-tuned open models, and prevents single-provider outages.
Alternative: One giant frontier model for every step with no cache or fallback — slow, expensive, fragile.
Breaks if: Caching stock or mixing embedding models across providers → stale inventory & broken cosine similarity.
AI-Native Workflow
12. "How do you use AI to get work done & know the bot is ready to ship?"
What: Spec constraints first (AGENTS.md), build in small verifiable increments, gate every prompt/model/search change with offline pytest + live shop eval (before/after numbers), log masked traces (turns.jsonl) to turn real user failures into new eval cases.
Why: AI writes boilerplate fast, but only tests, evals, and reading every diff catch real bugs (like the date guardrail false positive and Gemini PDF/thought-signature quirks).
Alternative: Manual "vibe-check" chatting after big AI edits — misses regressions in other intents silently.
Breaks if: Eval cases become stale or overfit to synthetic data → sample real production traces weekly (with PII masked) and cluster failure modes.

9.2 Backend, Database & Go Quick-Check (Central Tech Bonus Edge)

Central Tech tests backend & database concepts alongside AI (and their backend may use Go). Keep these crisp engineering points ready:

Database Indexes

Composite B-Tree Order

Put equality columns first, range column last: (category, in_stock, price). Always verify with EXPLAIN ANALYZE — watch out for leading-wildcard LIKE '%x%' full table scans.

Concurrency & Go

Python I/O vs Go Services

In Python, ThreadPoolExecutor bounds network I/O cleanly (index.py). In Go, the same pattern is a bounded worker pool of goroutines + context.WithTimeout + errgroup for parallel BM25 + vector calls + circuit breakers.

Caching & Sync

Event-Driven Freshness

Search results live in Redis with short TTL + invalidation on catalog updates. Live inventory & order status bypass cache (or use event-driven stock flags updated from POS/OMS queues like Kafka/PubSub).

Observability

What to Log Every Turn

Log masked input/output, tool calls + latencies, token counts, model/fallback used, guardrail triggers, and thumbs-up/down feedback — so you can find top failure clusters and turn them into eval cases.
